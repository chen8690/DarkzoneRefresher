读手机屏幕 → 比对规则表 → 不在池内就点 ↻ 刷新 → 三行都在池内就停手。
**只刷词条，绝不点「派遣」**——派遣由人工点。

## 1. 这个项目解决什么问题

在《暗区突围》「武装派遣」里挑装备时，「第一/第二/第三行」各有一件随机词条，想要的那几件
（枪 / 护甲 / 头盔背包）得反复点该行的 **↻ 刷新**赌出来，**每点一次扣 500 券**。规则写在桌面
Excel（`工作簿1.xlsx`）里，靠人盯着屏幕比对 + 连点，慢（实测一次刷新要 8.96 秒）、枯燥、容易看走眼。

本工具把这件事自动化：**用 adb 读手机屏幕 → OCR 认出三行装备 → 和规则表装备池比对 → 不在池内的
那一行才点 ↻ → 三行都在池内就停手**。

**边界（比功能更重要）**：

- **绝不点「派遣」**——三行就绪后停手，由人来点；
- **只管「武装派遣」的详情页**——先在手机上手动点「选择」进页；停在派遣列表上时一步都不走，直接报错；
- **默认不碰「暗区首领」那一栏**（用户 2026-10-11 的决定：「暗区首领那一栏彻底不管」）。只有显式加
  `--allow-list` 才走旧的「从列表页起步」流程，因为那条路会动到首领栏；
- **不选装备、不提交、不领奖**——除了「点该行 ↻」和「确认刷新弹窗」，不点任何别的东西。

## 2. 主要功能

| 功能 | 说明 |
|---|---|
| 免手点、读屏即判 | adb 截屏 + OCR（Windows 自带 OCR 或 RapidOCR）认出详情页三行装备名，不依赖游戏内任何插件 |
| 规则表驱动 | 装备池、排除名单、表头全部从 Excel 读（`darkzone/rules.py`），换池子只改表格，不改代码 |
| 逐行独立判定 | 三档各自比对自己的池；已在池内的行**一次都不点**（记 `refreshes=0`，真机省券） |
| 只在该点的时候点 | 点 ↻ 前必须连续读到「这一行不在池内」才动手，防 OCR 噪声白花 500 券 |
| 自动过刷新弹窗 | 点 ↻ 必弹「是否刷新特殊条件」模态框，只放行正文含「刷新」的框；别的框一律不点 |
| 花销台账 | 每次真刷新记 500 券，追加 `logs/task_ledger.jsonl`，结尾打印本次 + 跨次累计 |
| 报错即停手 | 画面没变、行数对不上、竖屏、等不到设备、连续无变化 → 一律停手报错，绝不硬刷 |
| 预演模式 | 不加 `--live` 就一次都不点，只打印「现在是什么 / 在不在池内 / 刷新键在哪」 |
| 双击即用 | `dry_run.bat` / `run_live.bat` / GUI（`darkzone_app.py`）三种入口 |
| 可加快 | 常驻 OCR worker（每屏 0.25–0.35 s）+ 常驻视频流取帧（读一屏 0.01 s）：一次刷新 8.96 s → **2.4 s** |
| 离线可测 | 7 个离线套件（假手机 / 合成截图），没有手机也能跑回归 |

## 4. 使用方法

### 4.1 先准备规则表

把想要的装备名填进 Excel。程序找规则表的顺序是：

1. `--rules` 指定的路径（给了就一定用它）；
2. 项目根目录的 `规则表.xlsx`（**推荐**：项目自带一份、打包时也会一起打进 `dist`）；
3. 桌面 `工作簿1.xlsx`（老习惯的兜底，跨机器时通常不存在）。

所以换台电脑只要把表放在项目根、名字叫 `规则表.xlsx` 就能直接跑，不用改代码。

| | A | B | C | D | E |
|---|---|---|---|---|---|
| 1 | 暗区首领 | 验证完暗区首领后 | 第一行装备选择 | 第二行装备选择 | 第三行装备选择 |
| 2 | 除了阿贾克斯和雷诺伊尔 | | AUG突击步枪 | BT101战术防弹衣 | 钢铁新星战术头盔 |
| 3 | | | SJ16栓动步枪 | 治安官重型防弹衣 | 野战登山背包 |
| 4 | | | AR30栓动步枪 | KN复合防弹衣 | RAL重型军用背包 |
| 5 | | | A545突击步枪 | AL指挥官弹挂甲 | |
| 6 | | | MK14射手步枪 | | |

- 表头行 A 列 = 类别，B 列 = 时机，C 列起 = 各档装备池（认「第N行装备选择 / 装备池 / 选项」这类表头）；
- 数据行 A 列 = 该块的限定条件（`阿贾克斯`、`雷诺伊尔` 这种名字会被解析成排除名单）；
- **一个池列 = 一档**，各档独立判定；行的实际名称不重要，靠「第几行」对齐。

### 4.2 跑

1. 手机连上电脑，`adb devices` 能列出设备；打开游戏，**手动点「选择」进入「武装派遣」详情页**；
2. **先预演**（不点任何东西）：双击 `dry_run.bat`，或

   ```powershell
   python -m darkzone.runner
   ```

   （想看程序挑了哪张表：加 `--rules "路径\规则表.xlsx"` 明说；不加就按上一节的顺序找。）

3. 看摘要里的「第N行 当前: xxx [OK / NG:不在池内]」和刷新键坐标都对，再**真机开刷**：

   ```powershell
   python -m darkzone.runner --live --limit 20
   ```

   或双击 `run_live.bat`（默认每行最多 40 次；`run_live.bat --limit 20` 改次数）。
4. 跑完看摘要：`status ready` = 三行都在池内，可以自己去点「派遣」了。

### 4.3 四种入口

| 入口 | 用途 |
|---|---|
| `dry_run.bat` | 预演：只读屏、算坐标、打印计划，一次都不点 |
| `run_live.bat` | 真机开刷（`--live`）；参数直接跟在后面，如 `run_live.bat --limit 20` |
| `run_ocr_rapid.bat` | 用项目 `.venv` 里的 RapidOCR 跑（更准、每屏 7–11 s） |
| `python darkzone_app.py` | 图形界面：设备状态、配置、日志、四个按钮（安全预演 / 真机运行 / 停止 / 清空日志），配置存 `app_config.json` |

三个 `.bat` 都**不写死解释器**：先找项目 `.venv\Scripts\python.exe`，没有就找
`%USERPROFILE%\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\python\python.exe`，再没有就用 PATH 里的 `python`。
（`.bat` 内容保持纯 ASCII —— cmd.exe 按系统代码页读批处理，中文容易把一行 echo 拆成两条命令；
`run_ocr_rapid.bat` 找不到 venv 会明确报错并退出 2，不会拿别的解释器跑到一半才失败。）

### 4.4 常用参数（`python -m darkzone.runner --help` 看全量）

> 中文 Windows 控制台默认 GBK，而帮助文本里有 `↻`：早期版本 `--help` 会直接抛
> `UnicodeEncodeError: 'gbk' codec can't encode character '\u21bb'`。现在 `runner.py` 开头统一做了
> `sys.stdout.reconfigure(errors="replace")`，打不出的字符退化成 `?`，不再打断运行（套件同理，见附录 A）。

| 参数 | 默认 | 作用 |
|---|---|---|
| `--rules` | 自动找表（项目根 `规则表.xlsx` → 桌面 `工作簿1.xlsx`） | 规则表路径 |
| `--live` | 关 | **不加就是预演**，绝不点击 |
| `--limit` | 40 | 每行刷新上限（每行单独计，不是总数） |
| `--serial` / `--wait-device` | 自动 / 60 | 指定设备序列号 / 等设备最多多少秒（等不到 exit 3） |
| `--image` + `--device` | — | 拿现成截图预演（离线），如 `--image samples\screen2_refresh_entries.jpg --device 3200x1440` |
| `--ocr {auto,rapid,win}` | `auto` | `auto`/`win` = 系统 OCR（快），`rapid` = RapidOCR（准）；也可用 `DARKZONE_OCR` 环境变量 |
| `--capture {auto,gzip,stream,fast,png}` | `auto` | `auto` = 视频流 → 设备端 gzip → 原始帧 → PNG 逐级回退（没有 ffmpeg 自动退 gzip） |
| `--wait-tap` / `--wait-screen` | 0.25 / 0.55 | 点击后、每次读屏后的等待秒数 |
| `--read-retries` | 8 | 画面没变时重读上限（每次间隔 0.7 s，画面一变立刻停） |
| `--settle-guard` | 0.9 | 点完「确定」先睡过动画窗口再信第一帧（`0` = 关） |
| `--settle-wait-change` | 3.0 | 点完「确定」后名字还没变就继续复读的预算秒数（`0` = 关） |
| `--confirm-reads` | 0=自动 | 花券前连续几次读到「不在池内」才允许点（`stream` 路自动取 2） |
| `--no-flush-pending` | 关（即默认会补确认） | 关掉「收尾补确认」，把最后一轮的确认框留给人工 |
| `--allow-list` | 关 | 走旧的「列表页起步」流程（会碰「暗区首领」栏） |
| `--dialog-mode {blind,read}` | `blind` | 确认框怎么处理：`blind` = 等 `--wait-dialog` 后**不读那一屏**直接点量好的「确定」坐标（快路，默认）；`read` = 老路，先读屏、只放行含「刷新」的框再点 |
| `--wait-dialog` | 0.85 | `blind` 路点完 ↻ 后等多少秒再点「确定」。**只能往小调、不能往大调**：2026-10-13 四次 live 实测这个框约 **1.0–1.4 s** 才画出来，而且**框已经在屏幕上时点它会被游戏吃掉**（1.0 / 1.3 / 1.9 三发全落到「框还在」的回落路；0.85 那发重新 OCR `ev_*_fastok*.jpg` 是 detail、点得进去）。点空也不要紧：复核那一屏会发现框还在，然后**回落**给 `read` 那条路（读框文字、只放行含「刷新」的框）再点一次 |
| `--fast-confirm` | — | 兼容旧脚本：等价于 `--dialog-mode blind`（盲点快路现在是默认，写了不改变行为） |
| `--no-sweep` | 关（即默认开启扫描兜底） | 关掉「点 ↻ 没反应就扫附近坐标」的兜底 |

### 4.5 返回码与安全阀

- 返回码：`0` = 完成或预演（`ready` / `dry_run`）、`2` = 其它失败（`incomplete` / `give_up` / `error`）、
  `3` = 等不到设备；
- 安全阀全部写死、不用配置，逐条见 [附录 A 的安全阀一节](#安全阀都写死了不用配置)
  （派遣禁点区、竖屏保护、行锚定、只认刷新弹窗、花券前再确认、时间闸门、收尾补确认…）。

### 安全阀（都写死了，不用配置）
- **不显式加 `--live` 就绝不点击**（`dry_run` 默认开）；
- **派遣保护**：任何落点离「派遣」按钮 3% 屏宽以内、或落进「派遣」矩形的禁点区，直接拒绝并报错退出；
- **竖屏保护**：截到竖屏（游戏没横过来/不在前台）直接报错，不瞎点；
- **刷新确认框**：真机上点 ↻ 必弹「提示 / 是否刷新特殊条件：xxx / 确定」模态框。只有正文含「刷新」、且不含 派遣/提交/出售/购买… 的弹窗才自动点「确定」（这种点击算生效，不会被误判成「点了没变化」）；点完确定弹窗还在 → 报错停手；
- **行锚定**：详情页按每行「点击装备」标签反推锚点取行（装备名在其上方 ≈7.2% 屏高）。解析出的行数 ≠ 槽位数就重读一次，仍不对 → `row_count_unexpected` 停手——**绝不猜着点**，因为行错位会刷错行、白花券；
- **「点了没变化」检测**：连续 3 次点击后全屏文字毫无变化（含顶栏资源数字）→ 判为点歪/有弹窗/资源不足，报错停止，不硬刷；
- **重读安全网**（2026-10-11 提速时加）：等待压短后可能读到「游戏还没把新画面画出来」的旧帧。读到既不是弹窗、文本签名又和点之前一样时，先按 `read_retry_delay` 每 0.7 秒重读一次、最多 8 次（≈5.6 秒，**画面一变就立刻停**），确认真的没变化才回去走扫描兜底——没有这层，读早了会被误判成「点空了」，扫描再点一次就白花 500 券。点「确定」之后同样重读（否则会误判弹窗还在 → 整轮 abort）；
- **花券前再确认**（2026-10-11 深夜加，`--confirm-reads`，`capture=stream` 时自动取 2）：点 ↻ 之前必须**连续**读到「这一行不在池内」才动手。起因是真机事故——视频流帧把 `AUG突击步枪` 读成 `AIJG突击步枪`（h264 糊了小字），模糊匹配对 3 个字母的核心容不下这种错，于是把**本来已经在池内**的一行判成「不在池内」，白刷一次花 500 券。多读一帧在流路上只要 0.01 s；读回来发现在池内就直接跳过并记 `confirm_in_pool`；
- **扫描兜底**：点 ↻ 没反应时按 `profiles\default.json` 的偏移量扫附近坐标，最多再试 2 个点（坐标已按真机像素核对过，不允许无限连点烧券）；
- **时间闸门 `settle_guard`**（2026-10-11 深夜加，默认 0.9 s，`--settle-guard 0` 可关）：真机是「顶栏先扣券 → 新词条过一会儿才画出来」，而流路读一帧只要 0.01 s，所以点完「确定」立刻读到的还是**刷新前的旧画面**；旧画面的读法和点前那次不一样（都是噪声），于是「签名变了 + settle 稳定」双双被骗过 → 把旧词条当成刷新结果（事故与死路见下）。规则：点了「确定」且这一屏走的是多读的取屏路时，先睡过动画窗口再读第一帧。**闸门挂在「点确定」这个动作里**（`_handle_dialog` + 盲点分支），不挂在调用点——17:21 那次真机验证就是挂错地方导致闸门一次没跑（见下）；
- **收尾补确认 `flush_pending`**（2026-10-11 深夜加，默认开，`--no-flush-pending` 可关）：一轮的**最后一次** ↻，确认框常在工具收尾之后才画出来（弹窗要 ~2 s），于是「券扣了、行没提交」——下一次启动会看到模态框而直接 abort（真机 `--limit 40` 第一次就是这么被挡下的）。规则：出报告之前多读一屏（`final_peek`），若还挂着**刷新确认框**就补点「确定」（这笔刷新本来就点过、钱也记了）并按补确认之后的真实词条**重判那一行**（原来那轮读到的可能是刷新前的旧行）；不是刷新框就只记 `pending_dialog_left`，交给人工，绝不自动点别的框。日志事件 `pending_dialog` / `final_recheck` / `pending_dialog_left`，报告里也会写 `pending_dialog`；
- 每次点击前后都留截图 + `logs\events.jsonl` 事件流，出问题按日志倒查。

### 组成

| 文件 | 作用 |
|---|---|
| `darkzone\rules.py` | 读规则表 → 规则块 / 装备池 / 排除名单 / 校验（`validate`） |
| `darkzone\ocr_match.py` | OCR 文本归一化 + 两道门控匹配（核心前缀按「带字类权重的编辑代价」判、类别尾巴必须**紧跟核心之后**），防止池外装备被误判成池内件 |
| `darkzone\win_ocr.ps1` / `win_ocr_worker.ps1` / `win_ocr.py` | 用 Windows 自带 OCR（zh-Hans-CN），不依赖任何第三方库。`win_ocr_worker.ps1` 是**常驻 worker**（引擎只加载一次，一行请求一行回答），默认走它：每屏 **0.25–0.35 s**；worker 不可用时自动回退 `win_ocr.ps1` 一次性进程（**0.9–1.2 s**），`DARKZONE_OCR_WORKER=0` 可强制走老路 |
| `darkzone\rapid_ocr.py` | RapidOCR（PP-OCRv4，onnxruntime，装在项目 `.venv`）后端，**每屏约 7–11 秒但更准**，接口和 `win_ocr` 完全一样 |
| `darkzone\ui.py` | 界面解析：列表页三栏 / 详情页三行 + 坐标换算（图片像素 → 真机像素）+ 跨引擎的标题合并 |
| `darkzone\runner.py` | 两段式主循环 + 安全阀（`python -m darkzone.runner`）；`--ocr {auto,rapid,win}` 选识别后端，`--wait-tap/--wait-screen/--read-retries/--capture` 调速度 |
| `darkzone\adb.py` / `source.py` / `stream.py` | adb 控制层（`screencap` 设备端 PNG / `screencap_fast` 原始帧+本地 JPEG / `screencap_gz` 设备端 gzip+本地解压）/ 屏幕来源抽象（真机 = LiveSource，`auto` 链 = stream→gzip→raw→PNG 逐级回退，离线 = ImageSource）/ `FrameStream` 视频流取帧（常驻 `screenrecord` + ffmpeg，读一屏 0.01 s；`LiveSource.last_chain` 记这一屏实际走的档，runner 靠它决定多读几次） |
| `darkzone\fake_screens.py` | 离线假手机：合成同版式截图 + 热区状态机 |
| `samples\ocr_rows_rapid.json` | **固化的真实 OCR 行**（两张真机截图 + 合成图 × 两个引擎），换引擎回归用 |
| `profiles\default.json` | 比例坐标（↻ 横向 0.910 等）+ 扫描偏移 |

> UTF-8** 脚本时按系统代码页（936）解码，脚本里的中文容易变乱码甚至语法错。所以脚本内部只用英文
> 提示、中文全放在 Python 侧；自己加 `.ps1` 时，含中文就存成 **UTF-8 with BOM**。

### 两个 OCR 引擎（2026-10-11 加）

| 引擎 | 怎么来的 | 每屏耗时（3200×1440，Core Ultra 5 125H 纯 CPU） | 特点 |
|---|---|---|---|
| Windows OCR | 系统自带 `Windows.Media.Ocr`，零依赖 | **1.2–1.7 s** | 中文准；汉字间会插空格、字母数字易错（`BT101`→`BTI01`、`SJ16`→`S」16`）——靠 `ocr_match` 的归一化兜住 |
| RapidOCR 1.4.4 | 项目 `.venv` 里 pip 装的 `rapidocr-onnxruntime`（PP-OCRv4 mobile，模型打进 whl，不用连 GitHub） | **7–11 s**（首次含加载模型 18 s） | 中文/字母数字都更准、不插空格（`BT101战术防弹衣` 直接读对）；代价是慢 7 倍 |

`--ocr` 三档（用户 2026-10-11 定：**默认用快的**）：
`auto` / `win` = Windows 自带 OCR（每屏 1.2–1.7 s；三次假阳性修完之后精度够用，`run_live.bat` 走这条）；
`rapid` = 项目 `.venv` 里的 RapidOCR（更准，每屏 7–11 s，用 `run_ocr_rapid.bat`）。
默认值也能用环境变量改：`DARKZONE_OCR=rapid`（离线套件就是用这个开关跑在 RapidOCR 下的）。
两条后端接口完全一样（`ocr_image` / `ocr_lines` / `line_text`），`darkzone\runner.py:Runner._pick_ocr` 负责挑。

换引擎踩到的坑（已修，`darkzone\ui.py:merge_split_labels`）：同一句标题
`暗区首领——伯纳德`，Windows OCR 读成一行，RapidOCR 读成两行（`暗区首领` + `伯纳德`，破折号还会丢），
于是详情页 boss 变成 `None`、列表页首领栏名字为空。现在按「只有标题没有名字 + 同一视觉行 + 紧贴右边」
把两行合回一行，对两个引擎都成立（`test_ocr_rows.py` 两边都钉住）。

### 一次刷新要花多久（2026-10-11 提速，用户要求「缩短每次点击时间，加快每次运行速度」）

一次刷新 = 点该行 ↻ → 读屏（弹窗）→ 点「确定」→ 读屏（新词条）→ 校验，也就是 **2 次读屏**。
**2026-10-13 起默认走盲点快路**（`--dialog-mode blind`）：省掉「读弹窗那一屏」的取屏 + OCR，
按量好的坐标直接点「确定」，再读一屏复核（框还在就回落给 `read` 那条路），流程变成
「点 ↻ → 点确定 → 复核一屏 → 读新词条」。
下表与实测数字都是 2026-10-11 那次提速、也就是**老路**的记录。

| 环节 | 旧 | 新 | 说明 |
|---|---|---|---|
| 取屏 | 设备端 PNG **2.30 s**（3.41 MB） | 设备端 `gzip -3` 压原始帧再传 = **1.39 s**（中位，见第 15 条） | 现在的默认路：`screencap \| gzip -3`（5.05 MB）→ 本地 `zlib` 解压 0.08 s → `PIL` 转 JPEG q90。旧快路 `Adb.screencap_fast`（原始帧 18.43 MB 直传 1.67 s + 转 JPEG 0.24 s = 1.91 s）降级为第二选择；三条路都失败才走设备端 PNG |
| 点击后等待 | 0.6 + 1.2 = **1.8 s** | 0.25 + 0.55 = **0.8 s** | 压短有风险（读早了会当成「点空了」），所以配了重读安全网 |
| OCR | 1.2–1.3 s | **0.25–0.35 s**（常驻 worker，2026-10-11 晚加，见下） | 慢的根源**不是**「扫了太多区域」，而是每次调用重付 ~0.6 s 的 powershell 进程启动 + WinRT 引擎加载：一张 **160×72** 的小图也要 0.54 s，全屏 0.87 s。改成常驻 worker 后全屏 0.27 s、右面板 0.13 s |
| **每次刷新合计** | **8.96 s**（跑#7：104 次刷新 932 s） | 默认路（流）**2.4 s 中位**；加时间闸门 ≈**3.3 s**（待真机复核）；`--capture gzip` 默认路 **5.42 s** | 真机实测，数字取自 runner 自己的 `charge` 事件 `sec` 字段（10 次流路刷新的中位）；中间态 ≈7.5 s 是「新取屏/新等待但还没上 worker」那次试跑；`logs\_speed_ab.py` 量取屏、`logs\_cycle_time.py` 量周期。**注**：这一行是 2026-10-11 的数字，当时盲点快路（**2026-10-13 起是默认路**）实测 5.19 s、当时的结论是不建议开 —— 那次是 `wait_dialog=0.7` 偏小点空导致的，2026-10-13 把它改成默认路、`wait_dialog` 提到 0.85，并配了复核+回落，理由见下 |

#### 常驻 OCR worker（2026-10-11 晚，用户要求「转向 ROI 识别」时查出真凶）

用户的原话是「识别慢的根源往往在于扫描了太多无关区域」。实测把这个假设**否掉了**：耗时基本与面积无关，
固定开销才是大头 —— 所以真正该省的是「每次调用重新起一个 powershell + 重新加载 WinRT 引擎」。
做法：`darkzone\win_ocr_worker.ps1` 常驻一个进程（引擎只加载一次，一行请求一行回答），
`win_ocr.py` 默认走它，起不来或中途挂掉就自动回退老的一次性进程（还会打印一行 `[warn]`）。

| 场景（同一张真机截图，3200×1440） | 一次性进程 | 常驻 worker | 省 |
|---|---|---|---|
| 全屏 | **0.94–1.15 s** | **0.25–0.58 s** | 0.37–0.78 s |
| 全屏（跑 5 次的稳态，`start_162831_890.jpg`） | 1.04 s | **0.28 s** | **0.76 s（3.7×）** |
| 右面板整条 1280×1440（原型实测） | 0.70 s | 0.13 s | 0.57 s |
| 右面板三行 1280×748（原型实测） | 0.67 s | 0.07 s | 0.60 s |

* 启动成本只付一次：worker 首次调用（含起进程 + 加载引擎）**1.03 s**，之后每次 0.25–0.58 s；
* **结果必须逐字节一样**：`logs\_worker_check.py` 拿 8 张真机/合成图对比「行文本 + 坐标 + 判页 + 池内判定」，
  两边**完全一致**（`FAIL 0`）——同一张图、同一个引擎，本来就不该有差异，有差异就是协议有 bug；
* 关掉它：`$env:DARKZONE_OCR_WORKER="0"`（runner 的 `start` 事件会记 `win_ocr_worker` 状态，便于核对）；
* 提速效果：`test_runner_offline`（整套跑一遍要 OCR 几十次）**54.4 s → 18.2 s**；
* **真机复测（2026-10-11 晚，花 1000 券经用户批准）**：同一张真机图、同一个槽2（未命中池内护甲），
  runner 自己上报一次刷新 —— 默认两段读屏路 `charge.sec = 5.42`（旧 8.96 s 的 60%），
  `--fast-confirm` 盲点路 `charge.sec = 3.57`（旧默认路的 40%，约 2.5×；`--fast-confirm` 是**当时的开关写法**，
  2026-10-13 起盲点是默认路 `--dialog-mode blind`）；
  两次 `done.elapsed_s` 分别 8.1 s / 6.1 s（含起进程、等设备、体检读屏一次）。

#### ROI 裁剪：实测是死路（记下来免得以后再试）

在同一张真机截图上把图裁成「只留右面板三行」甚至「160×72 的极小图」测下来：

| 裁剪 | 面积 | 一次性进程耗时 | 说明 |
|---|---|---|---|
| 全屏 3200×1440 | 100% | **0.69 s** | 29 行 |
| 右面板三行 1280×748 | 21% | 0.63 s | 12 行（丢了 boss、顶栏） |
| 三行带 + 顶栏 3200×892 | 62% | 0.77 s | 该留的都留了 |
| 极小 160×72 | 0.25% | **0.54 s（0 行）** | 面积只剩 0.25%，耗时还有全屏的 78% |

上了 worker 之后再裁，收益进一步被「解码 + 裁剪 + 另存 JPEG」吃掉：真机图实测**只省 0.01–0.15 s**
（`logs\_roi_parse_check.py`）。而且裁剪有两个真实风险（同一脚本跑出来的）：

1. `live_detail_hdr.png` 裁剪后第一行 ↻ 的 y 从 296 抖到 **292**（版面分析变了，坐标不该变却变了）；
2. `live_dialog.png` 裁剪后把「确定」按钮裁掉，弹窗页被判成**列表页** —— 这是危险方向。

结论：**不做 ROI 裁剪**；要提速就砍「读屏次数」（盲点快路，当时的开关 `--fast-confirm`，**2026-10-13 起是默认路** `--dialog-mode blind`）或取屏本身（现在的大头是设备端 1.9 s）。


还想再快就只能砍读屏次数——**盲点「确定」快路**（`--dialog-mode blind`，**2026-10-13 起是默认路**；
2026-10-11 用户点头加、当时默认关闭）：点完 ↻ 不读那一屏弹窗，等 `--wait-dialog`（默认 0.85 s）
后直接点 profile 里量好的确认框坐标（`dialog_confirm_xy_frac = [0.4975, 0.7167]`，即真机 (1592,1032)），
再读一屏拿新词条，**每次刷新 ≈4 秒**（2026-10-11 真机实测；坐标与路径不变）。代价与兜底
（2026-10-13 在默认路上重新量过一发对照：`blind` 0.85 是 **6.64 / 6.17 s**，`read` 老路是 **8.04 / 6.64 s**）：

* 这条路**不看弹窗文字就确认**——万一 ↻ 弹出的是别的框（理论上没有，真机每次都是「是否刷新特殊条件」），也会被点掉；
* 点完**读一屏复核**，这一屏按「框还在不在 + 行的名字变没变」分三种走法（`_blind_confirm`）：
  - 框还在 → 说明 0.85 s 等早了、点空了：**不重复点**，回落给 `_handle_dialog` 重读框文字、只放行含「刷新」的框；
  - 框没了、名字变了 → 命中，记账；
  - 框没了、名字还是旧的（动画窗口里新词条要 ~0.7 s 才落屏）→ 记 `blind_unclear`、**这一屏绝不记账**，
    按 `--settle-wait-change` 的预算继续读到名字真的变了才收（等出弹窗就同样回落到 `_handle_dialog`）；
* 「派遣」禁点区照旧生效（(1592,1032) 离派遣按钮 1134px，不在禁点区里）；
* **`--wait-dialog` 只能往小调、不能往大调**（2026-10-13 四次 live 实测）：这个框在点 ↻ 后约
  **1.0–1.4 s** 才画出来，而且**框已经在屏幕上时点它会被游戏吃掉**——重新 OCR 那一刻的
  `ev_*_fastok*.jpg`：0.85 s 那两发都是 detail（点得进去、盲点生效），1.0 / 1.3 / 1.9 那六发
  全是 dialog 且都落到 `blind_missed`（框还在 → 回落给读框路，多付一次取屏 + OCR，反而更慢）。
  实测 `charge.sec`：blind 0.85 → **6.64 / 6.17**；blind 1.0 → 6.34 / 5.63；blind 1.3 → 5.92 / 7.16；
  blind 1.9 → 5.37 / 6.0；`read` 对照 → 8.04 / 6.64。所以 0.85 是实测最好，别往上调；
* 想退回老路（先读屏、只放行含「刷新」的框）就写 `--dialog-mode read`；老开关 `--fast-confirm` 仍接受，
  等价于 `--dialog-mode blind`。
* 离线验证：假手机场景 **N**（`test_runner_offline.py`）断言盲点后**确实扣了 500 券**（说明「确定」真的点到）、槽1 只点一次 ↻、且**没有** `read_retry`（省的就是那次读屏）；
  场景 **P** 钉「点空回落照样刷到、且比 `read` 路快」，**P2** 钉 `dialog_mode=read` 仍然可用，
  **R3** 钉「框没了但名字还没变 → 不记账、等到新词条、不白刷第二次」。
* **真机验证（2026-10-11，500 券）**：`--live --fast-confirm --limit 1` 下槽2 刷 1 次，
  事件流是 `tap slot2_refresh1`(16:28:34) → `fast_confirm`(1592,1032) → `tap slot2_refresh1_fastok`
  →（0.8 s 后）只读一屏 → `charge` 500 券 → `row_check` 新词条 `AL制式弹挂甲`(16:28:38)，
  **一次刷新 4 秒**，全程没有 `auto_confirm`、没有 `read_retry`，也没碰「派遣」；累计台账 139000 券。

#### 视频流取帧 `--capture stream`（2026-10-11 深夜，用户选「从 scrcpy 视频流取帧」）

取屏的大头（设备端 gzip 1.39 s）本质是「每次都要重新压一张图再传 5 MB」。改成**常驻一条视频流**后，
读一屏只剩「拷贝一个已经写好的 JPEG」：

```text
adb -s <dev> exec-out "screenrecord --output-format=h264 --bit-rate 8M --time-limit 170 -"
        │  (h264 裸流)
        ▼
ffmpeg -f h264 -i - -vf fps=4 -q:v 5 -f image2 -update 1 -y logs\stream_frame.jpg
```

* 管道上**必须显式写 `-f h264`**：不写时 ffmpeg 在不可 seek 的管道上探不出格式，**一帧都不出且不报错**（踩过）；
* 代码在 `darkzone\stream.py`（`FrameStream`：`start/ensure/latest/stop/summary`），`LiveSource` 的链是
  `stream → gzip → raw → 设备端 PNG`，顺手失败只记一次 miss 并让这一屏退到下一档；
* **真机同屏 5 轮对照**（`logs\_stream_vs_gzip.py`，只读、0 券）：读一帧中位 **0.01 s**（gzip 1.3 s），
  三行齐全 5/5，用「红字像素带」量出的词条真实 y 与 gzip 路一致（297/521/745 vs 296/521/744）；
* 依赖外部 ffmpeg：`DARKZONE_FFMPEG` 环境变量 → PATH → 剪映自带的两份（`stream.py:FFMPEG_CANDIDATES`），
  都找不到就自动回退 gzip，不会报错；退出时 `stop()` 会 terminate 两个进程并 `pkill screenrecord`。

两个坑（都已修，且都留了回归夹具）：

1. **开头 ~1.5 s 是「坏帧窗口」**：刚起流的关键帧只有 ~154 KB（稳态 ~215 KB），实测**整行漏读第 1 行装备名**，
   而右侧面板表头「特殊习惯」被读成 `持殊习惯` 顶上来当第 1 行 → 三行 ↻ 变成 **400/522/624**（点错位置）。
   修法：`FrameStream.start(warmup=1.5)`：等满窗口、期间至少换过一帧；`darkzone\ui.py` 加
   `LABEL_FUZZY_MIN = 0.72` + `_fuzzy_detail_label()`，任何一个字之差的固定文案都不会被当成词条行。
   **窗口有多长是量出来的**（`logs\_stream_warm_sweep.py` → `logs\stream_warm_sweep_out.txt`，
   5 条新流 × 第一帧出现后每 0.25 s 取一帧判三行）：`t=0.00 s` 有坏的流 **5/5**
   （`KN复防弹衣`、`AIJG突击步枪`、`钢新星战木头盔`…），0.25 s 3/5、0.50 s 2/5、0.75 s 2/5、
   1.00 s 1/5、**1.50 s 0/5**。代价是每次起流多花 ~1.3 s（`start()` 2.6 s → 3.9 s，一轮只付一次）。
   这么修之后复测（`logs\_stream_warm_probe.py`，4 条新流）：`start()` 回来的第一帧 3/4 三行全对、
   再等一帧 3/4；稳态（`logs\_stream_fn_probe.py`，同一条流连读 15 帧）**15/15 帧三行全对**
   （改之前是 14/15），连续 3 帧都读错的组合 **0** —— 也就是说 `settle_reads` + `confirm_reads`
   这两道网几乎不需要开火。但坏帧是**随机**的（起流后仍可能碰到连续两帧读坏槽2），
   所以 confirm 网不能省：它兜住的代价最多是「白刷一次 500 券」，不会把池外判成池内。
2. **h264 会吃掉小字的笔画**：「点击装备」常被读成 `占击装备 / 击装备`（8M 与 16M、q1 与 q5 都一样，
   所以不是码率问题）→ 锚点扫描失效 → 几何兜底把按钮行当词条。修法：`is_tap_equip_label()`
   （`DETAIL_TAP_RE = [点占店]?击装备`）同时用于锚点扫描和 `parse_screen` 的判详情。
   词条名本身也会带噪声（`钢铁新星战木头盔`），由模糊匹配兜住（命中 `钢铁新星战术头盔`，score 0.95）。

* 夹具与回归：`samples\stream_first_frame.jpg`（退化首帧）、`samples\stream_steady.jpg`、
  `samples\gzip_detail_same_screen.jpg`，断言在 `darkzone\test_real_anchors.py`
  （首帧允许「行数不足」→ 交给 runner 的行数守卫重读/停手，但**绝不许**把固定文案当词条）；
* **2026-10-11 深夜改成默认**（用户定）：`auto` 链 = `stream → gzip → raw → 设备端 PNG`，
  没有 ffmpeg 的机器自动退到 gzip，不用改命令行；要强制老路就 `--capture gzip`（或 `png`）。
  真机只读预演 `logs\dryrun_stream_2.txt`（`--capture stream`）与 `logs\dryrun_auto_stream.txt`（不带参数）：
  判页 detail、boss 伯纳德、三行 ↻ = **297/520/744**、池内判定与 gzip 路一致、0 券；
* 为什么单屏 dry-run 反而慢（≈5.5 s vs gzip 2.7 s）：起流要等第一帧 + 1.5 s 坏帧窗口；
  它的收益只在**一次运行里读很多屏**的 live 跑里体现（每次刷新读 2–3 屏）。

**真机 live 实测（2026-10-11 深夜，`--capture stream --fast-confirm --limit 1`，`logs\live_stream_1.txt`）**：
两次刷新分别 **`charge.sec = 2.42` / `2.46`**（gzip + 盲点确定是 3.57 s，gzip 默认路 5.42 s）→
一次刷新 ≈**2.4 s**，是旧默认路的 **1/3.7**；`done.elapsed_s = 8.4`（含起流、等设备、体检读屏）；
流统计 `starts 1 / frames 5 / misses 0 / restarts 0 / stale 0 / alive true`，ffmpeg 用的是剪映那份。

这次跑也抓到一个**代价 500 券**的假阴性（所以有了 `--confirm-reads`）：流帧把槽1 的
`AUG突击步枪` 读成 **`AIJG突击步枪`**（h264 糊了小字笔画），模糊匹配对 3 个字母的核心容不下 2 个字符的错
→ 判「不在池内」→ 白点了一次 ↻（那一行本来是好的）。修法：**花券之前要求连续 `confirm_reads` 次
都读到「不在池内」**才允许点，`capture=stream` 时自动取 2（多读一帧在流路上只要 0.01 s，在 gzip 路上 1.4 s
所以默认不额外确认）。离线场景 **P**（`flaky_rows` 让第一帧故意画成坏名字）断言 0 券、一次 ↻ 都没点、
日志有 `confirm_in_pool`；对照组 **P2**（`confirm_reads=1`，老行为）断言确实白刷 500 券——
「为什么要多确认一次」就钉在测试里。

**真机 live 复测（默认路，`--limit 5`，全程无 `--capture`，`logs\live_stream_default_1.txt`）**：
`auto` 链确实走的流路（每个 `row_check` 事件都带 `chain: "stream"`）；十次 `charge.sec` =
2.61 / 1.67 / 7.71 / 2.45 / 2.34 / 2.33 / 2.11 / 7.03 / 1.73 / 4.96 → **中位 2.4 s**（两个 7 s 是
`read_retry` 那两次）；槽1/槽2 各刷 5 次（`--limit` 是**每行**上限）全部池外 give_up，
槽3 体检跳过，未点派遣；本次 **10 次 = 5000 券**，累计 **146000 券**。

#### 时间闸门 `settle_guard`：点完「确定」别信动画中间帧（500 券买来的教训）

真机的刷新顺序是**顶栏先扣券 → 新词条过一会儿才画出来**。流路读一帧只要 **0.01 s**，
所以点完「确定」立刻读到的还是**刷新前的旧画面**。危险在于：旧画面的读法和点前那次读法
**文本不一样**（都是 OCR 噪声），于是「全屏签名变了」和「settle 两帧稳定」**双双被骗过**，
把旧词条当成刷新结果 —— `logs\live_stream_1.txt` 就是这么白花了 500 券：

```text
17:03:53 只读预演   槽1 = AUG突击步枪（在池内 ✓）
```
